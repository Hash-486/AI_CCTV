| model | 640 | 960 | 1280 |

| yolo26s | **9.68 ms / 103 FPS** | 12.55 / 80 | 15.84 / 63 |

Detection speed alone does not settle the question, because higher `imgsz`
could produce larger person crops and crop size drives re-ID quality far more
than box placement does. It does not:

| model | res | median crop height | ≥64 px usable |
|---|---|---|---|
| yolo26s | 640 | **381.6 px** | 100.0% |
| yolo26s | 960 | 383.8 px | 98.7% |

**640 selected.** 960 and 1280 cost 30–64% more time and yield identically

960 made weapon detection *worse* (56% → 68% miss).

## 3. Real-time performance

`GHOST_FIXES` pipeline, `recordings/20260728_191730.avi`, ~3 people/frame:

| stage | ms/frame |
|---|---|
| OSNet embedding (batched, CUDA graph) | 3.33 |
| DeepSORT association | 0.74 |
| Identity resolution | 0.13 |
| **end-to-end, no pose** | **35.8 FPS** |
| **end-to-end, with MediaPipe** | **23.9 FPS** |

### CUDA graph capture — the optimisation that mattered

OSNet is **kernel-launch bound**, not compute bound. Its omni-scale blocks are
four parallel branches of depthwise-separable convolutions, repeated — an
enormous number of individually tiny operations. Two measurements prove it:

| | |
|---|---|
| batch 1 → batch 8 | 12.47 → 13.30 ms (8× work, +6% time) |
| osnet_x1_0 → osnet_x0_25 | 13.61 → 13.03 ms (16× fewer params, same speed) |

fp16 was also *slower* than fp32 (13.61 vs 12.21 ms). All three say the GPU is
idle waiting for launches, so neither a smaller model nor a smaller batch
helps. Capturing the forward pass as one replayable CUDA graph:

**12.91 ms → 2.66 ms, bit-identical output (max abs diff 0.00e+00).**

In-pipeline this took embedding from 34.88 to 3.33 ms/frame and the pipeline
from 16.7 to 35.8 FPS.

## 4. Ghost box elimination

Eight distinct causes were found in the base code. Symptoms reported were
"box lags behind a walker", "box bounces around after someone leaves", and
"random boxes when other people come in".

| # | cause | base location | fix |
|---|---|---|---|
| 1 | `to_ltrb()` returns the Kalman mean, not the detection | `tracker.py:396` | `to_ltrb(orig=True)` |
| 2 | `max_age=20` → 20 frames of velocity extrapolation | `config.py:24` | `max_age=5` + render gate |
| 3 | dead track latches onto a new person's detection | matching cascade | re-ID veto |
| 4 | `nms_max_overlap=1.0` disables DeepSORT's NMS | library default | `0.7` + output dedup |
| 5 | `n_init=2` confirms a 2-frame false positive | `config.py:25` | `n_init=3` |
| 6 | two tracks could claim one canonical id | `tracker.py:299-320` | Hungarian mutual exclusion |
| 7 | ghost filter blind for `time_since_update ∈ {1,2}` | `tracker.py:422` | moot under render gate |
| 8 | `{}` is not `None` → present person deleted | `tracker.py:414-426` | pose never deletes |
| 9 | liveness recorded after filtering → GC wiped live tracks | `:404` vs `:408` | record liveness first |

**The render gate is the primary fix**: a box is drawn only when its track
matched a real detection this frame, with a 2-frame coast permitted solely
when MediaPipe confirms a body at the predicted position.

Defect 8 is worth calling out because it caused the *opposite* symptom.
`kps = pose_cache.get(cid)` returning `{}` is not `None`, so a person the pose
model simply failed on scored 0 visible keypoints and was deleted from the
output. The same check produced both ghosting and vanishing.

## 5. Architecture change — one appearance model

The base ran **two** appearance CNNs per person per frame that shared nothing:
MobileNetV2 (1280-d, 224×224) inside DeepSORT for short-term association, and
OSNet (512-d, 256×128) outside it for identity.

This is worse than redundant. `ReIDGallery` keyed on `deepsort_track_id` and
only re-searched *unmapped* ids, so when MobileNetV2 swapped two people during
a short occlusion, the swapped-but-surviving track kept its canonical mapping
and **the gallery had no mechanism to detect or correct it**. The 15-frame
refresh then kept appending the wrong person's features to that identity,
progressively blending A into B. A short-gap association error silently
degraded long-gap re-acquisition.

Now: one batched OSNet pass per frame, injected into DeepSORT via
`update_tracks(embeds=...)` with `embedder=None`. Short-term association and
long-term identity share one re-ID representation.

### Weights

`build_model(pretrained=True)` loads **ImageNet** weights, not re-ID weights —
those are a separate download (`docs/MODEL_ZOO.md:41`) torchreid never fetches.
The base passed `model_path=""` and therefore ran ImageNet OSNet throughout.

Measured with true identity labels on both public benchmarks
(`benchmarks/bench_reid.py`, full standard protocol — Market-1501: 3,368
queries / 19,732 gallery; MSMT17: 11,659 / 82,161):

| weights | on Market-1501 | on MSMT17 |
|---|---|---|
| Market-1501 | **94.3 / 83.6** *(in-domain)* | 9.9 / 3.2 |
| **MSMT17** | 57.2 / 30.4 | **75.9 / 47.8** *(in-domain)* |
| DukeMTMC | 50.1 / 22.5 | 14.2 / 4.4 |
| ImageNet | 14.5 / 4.5 | 9.7 / 2.2 |

*(rank-1 % / mAP %)*

### Cross-domain transfer is asymmetric by 10×

The diagonal is unsurprising; the off-diagonal is the result that matters:

```
MSMT17 weights      -> Market-1501    30.4% mAP
Market-1501 weights -> MSMT17          3.2% mAP
```

Same architecture, same training procedure, opposite directions, a tenfold
difference. Market-trained weights out of domain (3.2%) barely exceed raw
ImageNet (2.2%) — a re-ID model trained on a narrow domain is close to
worthless outside it.

The cause is training-set diversity, not model quality. Market-1501 is a
single outdoor campus scene across 6 cameras. MSMT17 spans 4,101 identities,
15 cameras, indoor and outdoor, day and night. Variety produces features that
survive a domain change; a single scene produces features that memorise it.

**MSMT17 selected.** This deployment is a third domain that neither weight set
has seen, so only the cross-domain column predicts anything, and MSMT17 is the
only weight set that transfers. Selecting Market-1501 on its 94.3% would be
optimising for a benchmark this camera will never resemble.

Expected ceiling for an unseen indoor scene: **the 57.2 / 30.4 figure, not the
94.3 / 83.6 one.**

> An earlier version of this document selected MSMT17 for the right reason by
> accident. It cited intra/inter separability measured on `recordings/*.avi`,
> where ImageNet appeared to lead — noise on contaminated data. See §7.

## 6. Identity gallery

| property | value |
|---|---|
| representation | 512-d, L2-normalised |
| samples per person | 16, **diversity-selected** |
| memory | **~41.4 KB/person** (measured); 100 people ≈ **4.0 MB** |
| storage | RAM only, no disk, no database |
| lifetime | dormant identities expire 600 s after last seen; **active identities never expire** |
| capacity | 100 people, LRU eviction of dormant entries |

**Diversity eviction** replaces the base's FIFO. A new sample displaces the
most *redundant* incumbent rather than the oldest, so the set spans viewpoints
instead of holding 16 consecutive frames of one pose. Verified in
`tests/test_gallery.py[7]`: feeding 200 near-identical samples then 6 distinct
viewpoints then 50 more near-identical ones drops mean pairwise similarity
0.980 → 0.692 and retains 6/6 distinct views.

**Admission gating** replaces the base's admit-everything. A sample enters only
if the track matched a detection, crop height ≥ 64 px, confidence ≥ 0.5, the
box does not touch the frame border, and (when pose exists) ≥ 5 landmarks are
visible. Extraction still runs every frame; only storage is selective.

### New-identity decision

Three outcomes, not two:

```
MATCHED      s1 >= T_MATCH  AND  (s1 - s2) >= T_MARGIN
             AND the identity is unclaimed this frame
             AND the movement is temporally plausible
NEW          s1 < T_NEW
PROVISIONAL  otherwise -- hold up to DEFER_FRAMES, gather evidence, re-decide
```

The **margin test** is as important as the threshold. A score of 0.80 against
one candidate is evidence; 0.80 with a runner-up at 0.78 says the gallery
cannot tell two people apart, and committing would be a coin flip.

Assignment is solved **jointly** with the Hungarian algorithm over all pending
tracks, with temporal plausibility masked into the cost matrix rather than
applied as a post-hoc veto. Vetoing afterwards is wrong: when two tracks score
equally the tie breaks arbitrarily, so the solver can hand the identity to the
implausible track, which then fails the veto while the plausible track is left
evaluating a worse candidate — and both are incorrectly marked new. Caught by
`tests/test_gallery.py[3]`.

A second defect in the same joint solve was found by code review. After
Hungarian assignment, the margin test still compared against identities the
solve had awarded to **other** tracks. Two known people returning together:
track T8 scores I1=0.88 and I2=0.82, but I1 genuinely belongs to T7.
Hungarian correctly pairs T8→I2 at 0.82, comfortably above `T_MATCH`, yet the
margin test computed `s1 - s2 = 0.82 - 0.88 = -0.06`, failed, and returned
PROVISIONAL — creating a spurious duplicate identity `DEFER_FRAMES` later.
That is precisely the false split mutual exclusion exists to prevent, in the
two-similar-people case it was written for. An identity another track has
taken is unavailable, so it is not a competing explanation and now carries no
weight in the margin test. Regression test: `tests/test_gallery.py[3b]`.

### Body-proportion fusion — live, but unproven

Four scale-invariant ratios from MediaPipe landmarks (shoulder width / torso
length, hip / shoulder width, leg / torso, arm span / shoulder width) fused at
weight `0.15`. The term is **omitted entirely** when either side is
unmeasurable rather than replaced by a neutral constant — a term that cannot
discriminate must not silently shift the effective threshold, which is exactly
what it did in the base project.

**It was dead code until a review caught it.** `compute_body_ratios` was never
called and the query dicts never carried a `body_ratios` key, so
`REID_BODY_RATIO_WEIGHT` had no effect at all — reproducing the very flaw
criticised above. Now wired through `tracker._resolve_identities`, with the
same admission gate governing the geometry as the appearance samples.

Ablation on `clip1_short_reentry.avi`:

| `REID_USE_BODY_RATIOS` | re-entries | identities | frames producing ratios |
|---|---|---|---|
| `False` | 4/4 | 1 | 0 |
| `True` | 4/4 | 1 | **332** |

Confirmed live (332 frames vs 0) and confirmed **not load-bearing on this
clip** — appearance alone resolves every comparison, so a 15% contribution
cannot change the outcome.

Its value remains untested where theory says it should matter: two people in
**similar clothing**, where appearance collapses but skeletal proportions do
not, and backlit scenes, where geometry survives what lighting destroys.
Treat it as principled-but-unvalidated, not a demonstrated gain.

**22/22 unit tests pass.**

## 7. Re-identification accuracy on the deployment camera

`eval/eval_reid.py` over two clips recorded with `tools/capture.py` (raw
frames, no overlay), one person, eight annotated exit/return events with gaps
of 9.8–17.1 s. Thresholds are calibrated on this camera (§7a):

| metric | result |
|---|---|
| **re-identification accuracy** | **100.0%** (8/8 re-entry events) |
| false-split rate | 0.0% |
| false-merge rate | 0.0% (0 shared identities) |
| undecided rate | 0.0% |
| duplicate-id frames | 0 |
| identities created | **1 per clip** (for 1 person) |

Retention 100% at both measured gap lengths (3–10 s, n=7; 10–30 s, n=1).

### Lighting is the dominant variable — worth more than any tuning

The two clips are the same person performing the same actions, differing only
in where the light was. `clip1` was shot into a bright window; `clip9` has the
light behind the camera.

| | clip1 backlit | clip9 even light |
|---|---|---|
| median crop brightness | 120/255 | **154/255** |
| same-person long-gap similarity | 0.675 | **0.831** |
| 10th percentile (worst case) | 0.542 | **0.721** |
| per-event peak similarity | 0.769 / 0.815 / 0.851 / 0.851 | **0.954 / 0.913 / 0.952 / 0.928** |

**+0.156 mean similarity from moving a lamp.** That exceeds the combined
effect of every algorithmic change in this document.

Both clips score 100%, but the margins differ enormously. Backlit, three of
four re-entries cleared `T_MATCH` by under 0.07 — passing on almost no
headroom, the kind of result that holds until one condition shifts. Evenly
lit, every event clears by 0.16–0.20, and the *10th percentile* now sits where
the backlit *mean* was.

Against the separability bands in §9: backlit gives ~0.135, which those bands
call unusable; evenly lit gives ~0.29, which they call workable. The camera
crossed that line without a line of code changing.

**Practical consequence: camera placement and lighting are the deployment
risk, not the software.**

### Empty-scene ghost test

`clip8_empty_scene.avi` — 901 frames (45 s) at 30 FPS of the room with nobody
in it. The one test in this project with a **provable** answer: the correct
output is known in advance to be nothing, so any box is a false positive.

| metric | result |
|---|---|
| frames | 901 |
| raw detections | 6 |
| **rendered boxes** | **4 (0.44% of frames)** |
| **identities created** | **0** |
| persistent phantom tracks | 0 |

All four fall in a single 0.3 s window (frames 607–615) on a small dark object
entering at the right frame edge and moving downward — box travelling
`605,267 → 598,360`, height 63–66 px, confidence 0.32–0.57. Almost certainly a
hand or head briefly clipping the shot rather than a fabrication.

**The defensive result is that no identity was created.** The object was
side-truncated at the border and below the confidence bar, so gallery
admission rejected it; it rendered as an undecided box for four frames and
disappeared. That is the designed behaviour.

This addresses the original reported symptom — *"random boxes created when
there's no people"* — which described persistent phantom tracks that acquired
IDs and lingered. None occurred: 899 of 901 frames were completely clean, and
nothing was ever enrolled.

### Multi-person on this camera

`clip6_two_people_crossing.avi` — 653 frames, two people crossing repeatedly,
271 frames with both detected:

| metric | result |
|---|---|
| identities created | 3 (for 2 people — **one false split**) |
| duplicate-id frames | **0** (mutual-exclusion invariant held) |
| frames with 2+ tracked | 95 |

One false split is consistent with the calibrated 77.1% re-entry recall: at
that operating point roughly one re-acquisition in four is expected to fork.
The invariant that matters most held — no frame ever contained the same
canonical id twice, and no two people were merged.

This clip is also the source of every same-frame negative pair in §7a, so it
is what turned `T_MATCH` from an assumption into a measurement.

### Three bugs the first clip exposed

The first run scored **0/4 with 7 identities**. Each fix below was found by
measuring, not guessing, and all three were real defects.

**1. The admission gate rejected everything (`gallery.py`).**
`admitted: 0`, `rejected_admission: 1322`, of which 1,306 were `at_border`.
Every identity held **zero** samples, so there was nothing to match against
and every return necessarily created a new identity.

Cause: the subject filled the frame (median box height 469 px in a 480 px
frame), so the box touched an edge on nearly every frame, and the rule
rejected any box within 5 px of any edge. The intent was right — a clipped
body is a partial body — but the implementation was binary and treated
"standing close, head cropped" identically to "90% out of frame".

Fix: treat the axes differently, because they carry different information.
Side clipping (left/right) cuts the torso and is disqualifying. Vertical
clipping (top/bottom) removes head or feet, which OSNet tolerates well —
Market-1501 and MSMT17 crops routinely clip both — so it is now allowed
provided the box still has a person-like aspect ratio.

**2. Identity was decided from crops too poor to store (`tracker.py`).**
After fix 1 the gallery filled correctly (332 samples admitted, 16 per
identity) but `rematched` was still 0, while scores at each return reached
0.87–0.95 — far above `T_MATCH`. Those high scores were the track matching
the identity it had *just created*.

Cause: on re-entry the first detections are at the frame edge, i.e. partial
bodies. That fragment scored below `T_NEW` against the stored full-body
samples, taking the **immediate-NEW branch and bypassing the deferral band
entirely**. A new identity was committed within two frames; by the time the
person was fully visible and would have scored 0.95, the track was already
mapped and never re-queried.

Fix: gate identity *decisions* by the same quality bar as gallery
*admission*. A crop too poor to enrol is too poor to conclude "this is a
stranger" from. Tracks now stay unmapped until a usable view arrives, which
costs a few frames of an unlabelled box and avoids a wrong identity that
would persist for the whole track.

**3. The evaluation harness sampled identity during departures
(`eval/eval_reid.py`).**
After fixes 1 and 2 the pipeline created exactly **one** identity for one
person, yet the harness reported 1/4. It read the "before" identity from a
fixed offset (`exit_frame-30 … exit_frame-10`), which on event 4 landed while
the subject was already partway out of frame — provisional, therefore `None`
— and scored a perfectly maintained identity as a failure.

The measurement had inherited the very flaw the pipeline had just fixed.
It now scans outward for the nearest confidently-decided identity instead of
trusting an offset.

## 7a. Threshold calibration — measured on this camera

`benchmarks/calibrate_thresholds.py` on `clip6_two_people_crossing.avi` +
`clip9_even_lighting.avi`. The two-person clip is what makes this possible:
negatives are drawn only from crops in the **same frame**, which are
guaranteed to be different people, and a single-person clip contains none.

```
intra-person (all)      n=17492   mean 0.8405 +- 0.1127   (easy, short gaps)
intra-person (>=30f)    n=12655   mean 0.8203             (re-entry: governs T_MATCH)
inter-person same-frame n=   76   mean 0.6068 +- 0.0903
separability gap        +0.2135
best balanced accuracy   0.9033 @ 0.736
```

| false-merge budget | T_MATCH | re-entry recall |
|---|---|---|
| 0.1% | 0.7350 | 76.7% |
| **1.0%** | **0.7327** | **77.1%** |
| 5.0% | 0.7160 | 80.8% |
| 20.0% | 0.6946 | 85.0% |

The **flatness of that curve is the result**. Tightening the budget from 1% to
0.1% costs 0.4 percentage points of recall. On the old contaminated data the
same tightening cost a third of it (8.3% → 5.0%), because the distributions
overlapped so heavily that every threshold was a painful trade. Well-separated
distributions let you be strict about merging strangers and still recognise
nearly everyone who returns.

### Values now in `config.py`

| constant | placeholder | **calibrated** |
|---|---|---|
| `T_MATCH` | 0.75 | **0.7327** |
| `T_NEW` | 0.60 | **0.5617** |
| `T_MARGIN` | 0.10 | **0.0957** |
| `T_VETO` | 0.70 | **0.6636** |
| `DEEPSORT_MAX_COS_DIST` | 0.25 | **0.3735** |

At `T_MATCH`: **77.1% of true re-entries accepted, 1.32% false merges.**

The placeholders were close, but these are now measured properties of this
camera rather than assumptions. Re-run the script if the camera, lens or
lighting changes — §7 shows how much lighting alone moves the distributions.

**Caveat:** 76 same-frame negative pairs is a small sample. The direction and
magnitude are clear, but a longer two-person clip would tighten the estimate.

## 7a-i. The earlier negative result, and the reasoning error in it

The section below records the state **before** the clean clips existed, and
before the bugs they exposed were fixed. Its central claim — that
`recordings/*.avi` cannot support re-identification — remains true, and the
reasoning error is instructive.

**What it got wrong:** it concluded the pipeline was correct and only the data
was at fault. The data *was* bad, but the pipeline also had three real defects
that the bad data was masking. A dataset that fails for one reason can hide
others.

`benchmarks/calibrate_thresholds.py` on `recordings/*.avi`:

```
intra-person (all)    n=4202   mean 0.7239 +- 0.1403   (easy: short gaps)
intra-person (>=30f)  n=2607   mean 0.6511             (hard: re-entry)
inter-person          n=7621   mean 0.5370 +- 0.1038
separability gap      +0.1142
```

| false-merge budget | T_MATCH | easy recall | **re-entry recall** |
|---|---|---|---|
| 0.1% | 0.8649 | 23.5% | **5.0%** |
| 1.0% | 0.8139 | 30.5% | **8.3%** |
| 5.0% | 0.7310 | 43.9% | 20.9% |
| 10.0% | 0.6863 | 53.6% | 32.0% |
| 35.0% | 0.5633 | 85.8% | 77.9% |

**There is no usable operating point.** At a 1% false-merge budget only 8.3% of
real re-entries are recognised; reaching 78% requires accepting 35% false
merges, which permanently corrupts the gallery.

Confirmed end-to-end by `eval/occlusion_inject.py`: **0/5 identity retained**,
losing identity even at a 5-frame (0.17 s) occlusion. Instrumenting the gallery
showed why — a returning person scores **0.61–0.72** against their own stored
identity, entirely below `T_MATCH = 0.75`, so they sit provisional for 30
frames and are forced to a new id.

Two methodological errors were found and fixed while establishing this:

1. **Calibrating on easy positives.** The first version built the intra
   distribution from IoU-chained pairs, which are overwhelmingly short-gap, and
   recommended `T_MATCH = 0.8139` — *stricter* than the value that was already
   rejecting every re-entry. Splitting intra by temporal gap and setting
   `T_MATCH` from the long-gap tail is the fix.
2. **Mislabelled negatives.** IoU chaining fragments one person into several
   pseudo-ids, so cross-id pairs include same-person pairs. A model that
   correctly scores those high was *penalised for being right*, systematically
   favouring the worse embedder. Negatives are now restricted to same-frame
   crops, which are guaranteed distinct people.

### MobileNetV2 vs MobileNetV3 — settled on Market-1501

`benchmarks/bench_reid.py`, full standard protocol, real identity labels:

| embedder | dim | rank-1 | rank-5 | rank-10 | mAP | ms/img |
|---|---|---|---|---|---|---|
| OSNet x1_0 (Market-1501 wts) | 512 | 94.3% | 97.8% | 98.6% | **83.6%** | 1.56 |
| OSNet x1_0 (MSMT17 wts) | 512 | 57.2% | 73.8% | 79.7% | 30.4% | 0.75 |
| OSNet x1_0 (Duke wts) | 512 | 50.1% | 66.8% | 73.4% | 22.5% | 0.64 |
| OSNet x1_0 (ImageNet) | 512 | 14.5% | 27.8% | 34.3% | 4.5% | 0.64 |
| MobileNetV3-S (ImageNet) | 576 | 11.5% | 22.9% | 30.1% | 3.5% | 0.47 |
| MobileNetV3-L (ImageNet) | 960 | 9.8% | 18.9% | 24.7% | 2.6% | 0.68 |
| MobileNetV2 (ImageNet) | 1280 | 6.8% | 15.3% | 20.5% | 2.2% | 0.88 |

**MobileNetV3-Large marginally beats MobileNetV2 (2.6% vs 2.2% mAP), and
neither is usable for re-identification.** Both are roughly 12× worse than
cross-domain OSNet and 32× worse than in-domain OSNet. The base pipeline was
performing short-term identity association with a model that scores 2.2% mAP
at telling people apart — which is the mechanism behind the gallery poisoning
described in §5.

This also **validates the implementation, twice**:

| benchmark | measured | published (MODEL_ZOO) |
|---|---|---|
| Market-1501, Market weights | 94.3 / 83.6 | 94.2 / 82.6 |
| MSMT17, MSMT17 weights | 75.9 / 47.8 | 74.9 / 43.8 |

Reproducing two independent references to within 1.0% rank-1 confirms model
loading, cv2 preprocessing, ImageNet normalisation, L2 handling, the
CUDA-graph replay path and the CMC/mAP protocol are all correct. Any
remaining re-identification failure is therefore attributable to the input
data, not to the implementation.

Two practical notes: torchreid ships **no** MobileNetV3, so V3 requires a
custom torchvision wrapper; and torchreid's MobileNetV2 is a **dead network**
(output max 8.1e-9, all activations collapsed), excluded rather than scored.

#### This reverses an earlier finding in this document

`benchmarks/bench_embedders.py`, using IoU-chained pseudo-labels on
`recordings/*.avi`, ranked **MobileNetV3-L first** (separability 0.428) and
OSNet-MSMT17 last (0.205). With real labels that ordering is exactly
inverted, by a factor of 12.

The cause is a labelling bias, not sampling noise. IoU chaining fragments one
person into several pseudo-identities whenever the chain breaks, so pairs
between fragments *of the same person* were labelled "different people". A
model that correctly scores those pairs high was therefore **penalised for
being right**, systematically favouring the weaker embedder. Restricting
negatives to same-frame crops reduced the bias but left only 85 negative
pairs — too few to rank anything.

The lesson is recorded here because it applies to the whole evaluation: a
metric computed from labels produced by the system under test will flatter
whatever the system already does.

## 7b. Tracking and re-ID on MOT17 — real annotated video

Market-1501 and MSMT17 are pre-cropped stills, so they score the embedder but
cannot score the tracker. MOT17 is full-frame surveillance video with
per-frame human-annotated identity ground truth, which is the only source here
that exercises the whole pipeline: detection, association, occlusion,
entries and exits, and multiple people in one shot.

Static-camera sequences only (`eval/eval_mot.py`). MOT17-05/10/11/13 use a
moving platform, which is a different problem from a fixed install.

| sequence | people/frame | IDF1 | MOTA | recall | IDSW | MT/ML | re-entry |
|---|---|---|---|---|---|---|---|
| MOT17-09 (mall) | ~10 | **81.0%** | 62.9% | 84.7% | 4 | 14/4 | **1/1** |
| MOT17-02 (street) | ~20 | 57.6% | 36.8% | 44.0% | 12 | 13/28 | – |
| MOT17-04 (night) | ~45 | 45.6% | 29.1% | 31.4% | 25 | 9/43 | – |

Published MOT17 trackers typically report IDF1 in the 60–80% range, so
MOT17-09 at 81.0% is competitive — and this uses our own detector rather than
the benchmark's supplied public detections.

### Recall is the bottleneck, not identity

IDF1 tracks recall almost exactly across the three sequences
(84.7→81.0, 44.0→57.6, 31.4→45.6). ID switches stay low relative to identity
count (4, 12, 25 against 18, 53, 79 identities). The tracker is not losing
people's identities; the **detector never sees them**.

### Detector resolution must match source resolution

MOT17 is 1920×1080. Running `imgsz=640` downscales 3×, shrinking distant
pedestrians below detectability. MOT17-02, first 300 frames:

| imgsz | IDF1 | MOTA | recall |
|---|---|---|---|
| 640 | 54.0% | 33.5% | 40.6% |
| **1280** | **66.5%** | **45.7%** | **57.3%** |

**This does not overturn the 640 decision in §2, but it does narrow it.**
640 is correct for a 640×480 camera, where it is already native and higher
values only interpolate. The general rule is to match `imgsz` to the source:
640 here, 1280 for 1080p input. `INFER_IMGSZ` in `config.py` is set for the
deployment camera; change it when processing higher-resolution footage.

### Caveat on the metrics

IDF1 here is computed by dominant-identity assignment rather than the official
TrackEval bipartite-matching implementation, so it is indicative rather than
leaderboard-comparable. MOTA, IDSW, MT/ML and recall follow the standard
definitions. Ground truth is filtered to class 1 (pedestrian) with `conf==1`
and visibility ≥ 0.25, as the benchmark protocol requires.

## 8. Data limitations

**Resolved.** The predictions in this section were tested and held: clean
footage recorded with `tools/capture.py` lifted separability from 0.114 to
**0.2135** and re-entry recall at a 1% false-merge budget from **8.3% to
77.1%** (§7a). The section is kept because it records the reasoning, and
because one part of it was wrong in an instructive way — see §7a-i.

The rest of this section describes the superseded `recordings/*.avi` data.

Every **PROVISIONAL** number above was measured on `recordings/*.avi`, which
are the *old pipeline's annotated output*: green skeletons, bounding boxes, ID
labels and a status bar are drawn into the pixels. Every crop fed to the re-ID
model contains drawn graphics.

Compounding this:

- three of four clips contain **one person**, so inter-person pairs come from a
  single clip;
- **nobody ever leaves and returns**, so the case the system exists to handle
  is never exercised in the source data;
- pseudo-identities come from IoU chaining, which both fragments people and can
  merge them through a crossing.

**The pipeline is correct; the data cannot support the task.** Separability of
0.114 is below the threshold at which any re-identification system works, and
that is a property of the footage, not of the code.

### This is now measured, not assumed

Until Market-1501 was added, "the model is fine, the data is bad" was an
inference. The two possibilities looked identical from inside this project:

| | implication |
|---|---|
| the embedding model is weak | more footage will not help; change the model |
| the scene/source video is weak | the model is fine; better footage will help |

Running the *same* embedder against clean labelled data separates them:

```
OSNet x1_0, in-domain             mAP 83.6%  (Market) / 47.8%  (MSMT17)
OSNet x1_0, cross-domain          mAP 30.4%  (MSMT17 weights -> Market)
OSNet x1_0, on recordings/*.avi   separability 0.114  (unusable)
```

A model that reaches 83.6% mAP on clean data and 30.4% on an unseen domain is
not the bottleneck. **Recording clean footage will help.**

The whole-pipeline version of the same comparison is starker still. Identical
code, two inputs:

| input | result |
|---|---|
| MOT17-09 (annotated surveillance video) | **IDF1 81.0%**, re-entry **1/1** |
| `recordings/*.avi` (this project's own) | separability 0.114, retention **0/5** |

The pipeline is not the variable.

Set expectations from the cross-domain figure, not the in-domain one. Your
scene is a third domain, and an indoor low-resolution CCTV view is plausibly
harder than either public benchmark, so **~30% mAP is an optimistic target and
not a floor**. If clean footage still yields separability under 0.15, the
remaining lever is camera placement — people need to occupy more vertical
pixels — rather than more data or a different model.

## 9. Separability, and what remains

Separability — long-gap intra mean minus inter mean — is the single number
that predicts whether re-identification can work at all on a given setup:

| gap | verdict | measured here |
|---|---|---|
| < 0.15 | unusable | `recordings/*.avi` **0.114**; backlit clip1 ~0.135 |
| 0.15–0.25 | marginal | **this camera, well lit: 0.2135** |
| 0.25–0.35 | workable | |
| > 0.35 | good | |

At 0.2135 the system works — 100% on eight recorded re-entry events — but sits
in the marginal band, which is consistent with the one false split seen on the
two-person clip. The levers that would move it further, in order of measured
effect:

1. **Lighting** — worth +0.156 similarity for the cost of moving a lamp (§7).
2. **Framing** — people must be fully in frame. A take aimed at a wall 2 m away
   produced inter-person similarity of 0.700, because the embeddings were
   describing the doorway rather than either person.
3. **Camera height** — untested. OSNet's training data is mostly elevated
   surveillance, so a downward angle may suit it better than eye level.

### Still open

- **Similar-clothing clip.** The hardest case, and where the body-proportion
  fusion (§6) would first earn its place.
- **Sample size.** 76 same-frame negative pairs; a longer two-person clip
  would tighten the calibration.

### Regenerating everything

```bash
python benchmarks/calibrate_thresholds.py --clips eval/clips/clip6_two_people_crossing.avi \
                                                  eval/clips/clip9_even_lighting.avi
# copy recommended values into config.py
python eval/eval_reid.py --clips eval/clips --gt eval/ground_truth
python eval/eval_mot.py --seq MOT17-09-FRCNN
python benchmarks/bench_reid.py --dataset market1501
python benchmarks/bench_reid.py --dataset msmt17
```

Calibrate on well-lit, well-framed clips only. Pooling a backlit clip's
positives with a well-lit clip's negatives mixes conditions and understates
separability — doing exactly that produced a misleading 0.0626.
